## Organisation de la documentation

Deux tiers, puis neuf catégories fonctionnelles.

| Niveau | Contenu |
|---|---|
| **Foundations** | Couleur, typographie, espacement, rayons, largeurs, conteneurs, effets, motion. Les décisions de design — aucun composant. |
| **Les neuf catégories** | Actions · Données · Étiquettes · Feedback & chargement · Identité & média · Navigation · Saisie · Structure · Superposition |

Les catégories répondent à **« où est la chose qui fait X ? »**. C'est la question de celui qui
cherche ; « quel est son degré de composition ? » est celle du mainteneur, et elle est portée par le
tag `primitive`.

Une pièce qui n'existe qu'à l'intérieur d'un parent est rangée **sous ce parent** —
`Actions/ButtonGroup/Item`, `Superposition/Dropdown/Item`, `Saisie/InputDropdown/SelectItem`. Il n'y
a pas de tier « sous-composants » : aucun des systèmes comparés n'en a, et la règle « ne s'utilise
jamais seul » se lit mieux à côté du parent.

L'ordre du volet est figé dans `.storybook/preview.ts` (`options.storySort`). Les catégories sont
alphabétiques par choix : tout classement « par importance » finit par se discuter, et la
prévisibilité est justement l'objectif. L'ordre des stories *à l'intérieur* d'un fichier reste celui
du code, jamais alphabétique.

## Graphiques et cartes : quelle pièce ?

Le design system fournit **l'habillage** des données, jamais le moteur qui les trace (ADR-0006) — à
une exception près, `Sparkline`, une ligne trop petite pour qu'un moteur vaille la peine.

| Besoin | Pièce | Ce qu'elle dessine |
|---|---|---|
| Un graphique où l'on **lit des valeurs** | `ChartFrame` + le tracé du moteur | Titre, description, légende, axes, grille, chargement, vide — pas les données |
| Nommer les séries d'un graphique | `ChartLegend` (dans `ChartFrame`) | Une marque et un mot par série |
| La valeur sous le pointeur, sur un graphique | `ChartTooltip` (placée par le moteur) | Une valeur héros, des séries — ne contient rien de cliquable |
| **La tendance d'un chiffre** déjà dit à côté | `Sparkline`, seule | Une ligne et sa comparaison en pointillé — ni axe, ni titre, ni interaction |
| La couleur d'une grandeur sur une carte | `ColorScale` | Un dégradé, ses valeurs, la clé des symboles |
| Ce que dit un **clic** sur un point de carte | `MapTooltip` (placée par le moteur) | Un petit dialogue : titre, fermer, lignes marque · mot · valeur |

`ChartFrame` et `Sparkline` ne s'emboîtent pas : une sparkline encadrée gagnerait des axes, un cadre qui
dessinerait sa courbe serait un moteur. Quand une ligne a besoin d'un axe, d'une légende ou d'une
infobulle, c'est un graphique.

## Icônes

Le jeu d'icônes est [Lucide](https://lucide.dev) (ISC) — **189 icônes**, exactement le sous-ensemble
publié dans la frame Figma `Icons/Lucide`, pas la bibliothèque entière.

Les fichiers sont **générés**, jamais écrits à la main :

```bash
# 1. ajouter/retirer un nom Lucide dans scripts/icons.manifest.txt
# 2. régénérer
npm run icons
```

Quatre tailles : `16 | 20 | 24 | 32`. Les icônes sont dessinées sur une grille de 24px en
`stroke-width: 2` et le stroke suit la boîte — le stroke effectif vaut donc `2 × taille / 24`
(1,33 / 1,67 / 2,00 / 2,67). Il n'est pas compensé aux petites tailles. Les glyphes *à l'intérieur*
d'un contrôle (coche de `Checkbox`, fermeture de `Tag`) sont des ornements et échappent au plancher
de 16px.

## Artwork des modules

`ModuleIcon` porte les deux niveaux publiés dans Figma, sur le modèle des tokens :
`variant="illustration"` est la **primitive** (le dessin seul), `variant="logo"` la **sémantique**
(le même dessin sur sa tuile) — et c'est la valeur par défaut.

Comme les icônes, les fichiers sont générés depuis les exports Figma bruts :

```bash
npm run module-art
```

11 modules. `Eudr` est absent de `ModuleName` : la variante est vide dans Figma et son artwork se
trouve en réalité sur `Trace` — voir ADR-0005.

## Architecture des tokens

Les tokens sont organisés en deux niveaux :

**Primitives** — les valeurs brutes de la palette (couleurs, typographie, espacement, effets). Ne sont jamais utilisées directement dans les composants.

**Sémantiques** — les usages nommés (`bg-brand-solid`, `fg-secondary`, `border-error`…) qui référencent les primitives. Ce sont ces tokens que les composants consomment.

Tous les tokens sont préfixés `--ds-` et exposés comme variables CSS sur `:root`.

Après toute modification des sources de tokens :

```bash
npm run tokens
```

## Statut des composants

Le statut vit sur les stories, pas dans un tableau. Chaque composant porte exactement un tag —
`stable` ou `wip` — et le volet latéral de Storybook sait filtrer dessus.

| Tag | Sens | Compte |
|---|---|---|
| `stable` | Documenté, testé, utilisable en production | 10 |
| `wip` | Fonctionnel, documentation incomplète. Peut évoluer sans préavis | 43 |
| `primitive` | Élément unique, sans composition ni état interne — sûr comme socle | 8 |

Ce tableau comptait auparavant les composants à la main. Il en déclarait 42 en WIP quand
Storybook n'en marquait que 8 : deux sources de vérité qui divergeaient sans que rien ne le
signale. Une seule les porte désormais, et c'est celle qui est à côté du code.

`primitive` est un axe séparé, pas un niveau de maturité : il remplace l'ancien tier `Primitives`
et se combine avec l'un des deux statuts.

## Contribuer

Le dépôt est ouvert aux contributions internes. Pour ajouter un composant :

1. Créer le dossier `components/NomComposant/`
2. Ajouter `NomComposant.vue`, `NomComposant.stories.ts`, et `NomComposant.mdx`
3. Exporter depuis `components/index.ts`
4. Ouvrir une PR sur [GitHub](https://github.com/Abi-shai/tolbi-design-system)

Un composant est **stable** quand sa page MDX est présente et sa description dédupliquée.
